# 依赖检查说明

## 安全公告与维护状态

- 以当前 Composer 返回的 JSON 为准；公告通常在 `advisories` 中按包分组，废弃包信息可能在 `abandoned` 中。不要依赖输出颜色或固定的历史 JSON 示例。
- 记录包名、实际版本、公告标识、公告链接、受影响版本、已发布的修复版本。公告没有严重度时标为“待确认”，不要按漏洞名称自行推定 CVSS 分数。
- 根据公告、依赖关系和静态源码证据提出升级或替换建议。公开公告有明确修复版本时优先使用；未提供修复方案时说明限制。
- 直接、间接、生产和开发依赖分别标注，但这些分类不能单独决定风险。开发工具可能在 CI 或构建流程中处理不可信输入。
- `abandoned` 表示维护风险，不等于已确认漏洞。使用返回的替代包建议，并核对是否符合项目 API 和 PHP 版本约束。
- `audit` 非零退出可能表示发现公告或废弃包；应结合正文和错误输出解释，不只看退出码。

## 过期依赖与版本约束

- 有锁文件时使用 `outdated --locked`，避免误把缺少 `vendor/` 当成项目没有依赖。`--direct` 限制为直接依赖，完整扫描再包含间接依赖。
- 按包的版本策略解读当前版本、最新版本和 `latest-status`；大版本更新说明需要兼容性评估，不自动构成重要缺陷。
- 检查宽泛或精确约束的实际意图。`*`、无上界约束和精确锁定值得核实，不一律报错；例如 `6.3.*` 只允许 `6.3.x`，不是允许任意 `6.x`。
- 应用通常依靠锁文件实现可重复安装；库通常需要在声明的兼容范围内支持多个下游环境。不要仅为追新收紧库的生产依赖范围。
- 检查 `minimum-stability`、`prefer-stable`、`config.platform`、扩展要求及 `require-dev` 的归属，结合实际部署与框架约定给出建议。
- 锁文件不同步应报告；审计阶段不运行 `update`、`require`、`bump` 或 `install` 来掩盖问题。

## PHP 目标版本

用户有明确目标时，执行 `composer prohibits php TARGET_VERSION` 并沿阻塞依赖链解释原因。没有阻塞只说明依赖约束允许该版本，不证明应用、扩展和运行环境兼容。不要使用 `--ignore-platform-reqs` 绕过兼容性判断。
