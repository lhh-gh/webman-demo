# 代码质量说明

## 先看兼容性与行为

以 `require.php` 支持的最低版本为语法基线，同时核对 CI、`config.platform` 和部署环境。当前机器支持某项语法，不代表项目可以使用它。

| 特性 | 最低 PHP 版本 |
| --- | --- |
| 参数、返回值的标量类型，`strict_types` | 7.0 |
| 类型化属性、箭头函数 | 7.4 |
| 构造函数属性提升、`match`、命名参数、nullsafe、联合类型、原生 attributes | 8.0 |
| 枚举、readonly 属性、交集类型、first-class callable、`never` | 8.1 |
| readonly 类、DNF 类型、独立 `true`/`false`/`null` 类型 | 8.2 |
| 类型化类常量、`#[\Override]` | 8.3 |
| 属性钩子、非对称属性可见性、`#[\Deprecated]` | 8.4 |

- 缺少类型不是运行错误的直接证据。添加参数或返回类型前检查继承、框架接口、调用方和公共 API。
- `strict_types` 会改变调用方文件中的标量类型检查行为，不可批量添加而不审查兼容性。
- `match` 使用严格比较；不能直接替换依赖宽松比较或 fall-through 的 `switch`。
- `readonly` 需要确认初始化与后续写入行为；常量改枚举会影响参数、持久化及序列化契约。

## 有证据的检查

- 对照实际 PSR-4、classmap、files 配置核实路径与命名空间；考虑本项目 `app\\` 与 `App\\` 的框架约定。
- 从入口、核心服务和数据访问代码抽样，审查输入边界、参数绑定、返回值、异常处理和外部资源释放；模式搜索只用于找候选，不能单靠命中确认缺陷。
- 错误抑制符需要结合后续返回值处理评估；不要不理解原有恢复逻辑就删除。
- 性能结论需要数据规模、调用方式或测量依据。数组函数不保证比循环快；生成器减少逐项产出时的内存需求，不保证整个调用链恒定内存。
- 类长度、构造参数数量和缺少依赖注入只是线索；只有解释了可维护性问题和受影响行为，才提出重构建议。
- 优先使用已有 PHPStan、Psalm、代码风格或测试配置。诊断不运行自动修复，不为审计临时引入依赖。
- 测试和迁移按本次目标决定是否检查；不要全局豁免。第三方和生成代码通常只记录问题归属，不手改。

避免只有“改用最新语法”的发现。建议必须说明项目为何受益、兼容范围以及验证方式。
