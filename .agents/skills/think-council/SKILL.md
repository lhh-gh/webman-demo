# Think Council：多视角讨论团

作为主持人，根据问题设计互补视角，把分析汇总为可供用户决策的结论。

## 范围与讨论方式

- 本技能属于包含 `.agents/skills/think-council/` 的当前仓库。讨论只需分析时，不因此修改代码、提交、启动服务或联系外部人员。
- 先提炼待决策的问题、已知约束和判断标准。结合已有会话消除可推断的信息缺口；只有缺失信息会显著改变建议时才澄清。
- 默认一次完成视角设计、各视角分析、必要的交叉核对和总结。用户明确选择“逐轮讨论”或要求检查点时，按其选择停留并等待回应；用户已说“继续”或“一次完成”时不重复要求确认。
- 默认由当前 Codex 从多个视角分析，明确这是同一代理的多视角分析，不称为已获得多名独立专家或多个模型验证。
- 只有用户明确要求并行子代理且会话支持时才使用可用的代理协作工具，不依赖 Claude 的 `Task`、`Agent` 或 `AskUserQuestion` 工具名称。否则在当前代理内完成。

## 选择互补视角

通常选择 3–5 个关键视角；用户要求的人数优先。以覆盖决策标准为目标，不为凑人数添加重复角色。

例如仓库技术选型可考虑：业务效果、维护与架构、运行可靠性、实施成本、使用体验。按实际问题调整，不固定套用这些角色。每个视角说明关注点和为何必要，不预设正反双方。

涉及仓库事实时先收集必要证据。存在 `.codegraph/` 时，在理解或定位源码前先用 CodeGraph；不存在则按需使用 `rg` 与文件读取，不创建索引。引用当前文件位置或其他可核查来源，区分事实、假设和推测。

## 各视角分析

每个视角给出简明、面向用户的结果：

- 核心判断与支持依据。
- 依赖的关键假设和未知信息。
- 该视角发现的独特风险、收益或遗漏。
- 什么新证据会改变这一判断。

当前代理依次分析时，保留各视角差异，但不声称它们具备真正的盲评独立性。输出结论、证据与简要理由即可。

若用户要求并实际使用了子代理：给每位代理相同的原始问题、约束和原始证据，加上各自关注点；首轮不提供其他代理结论或主持人的预期答案。分工为只读分析，不让它们修改共享文件。按可用并发数分批，并如实说明哪些分析实际并行完成。

## 按实际内容核对分歧

只讨论已经出现的实质差异：对同一事实判断不同、依赖的假设冲突，或某个方案遗漏了另一视角提出的关键因素。

用简短列表或对比表列出“争议点、依据、成立条件、待验证信息”。不按角色身份安排对抗，不为热闹编造争议。观点一致时如实说明，并核对是否共同依赖了未验证假设；一致不等于方案已被证明正确。

## 给出可执行结论

按任务需要简洁呈现：

- 当前建议及适用条件。
- 已形成的共识与仍存在的主要分歧。
- 最关键的假设和证据缺口。
- 如何验证，以及验证后如何选择。
- 可在现有授权范围内执行的下一步。

不要只复述角色发言。信息不足时给出条件性结论；用户只要求评估时，以评估完成为止。用户补充信息后，只更新受影响的视角和结论，说明变化及原因，不默认从头重跑全部讨论。
